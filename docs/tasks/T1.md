# T1 — fixtures through the one door

## Goal

Three committed fixtures as `Session`s with pre-labeled items, produced by the Claude Code JSONL
adapter and a manual build script, with expected answers in pending tests the analyzer cannot
see. Each demo tells one story; the picker shows three. This task pushes back on the contract
types before `/freeze-contract`.

## Mechanics (agreed)

- Adapter `src/adapters/claude-code-jsonl/` (parse, to-session, redact, index), pure, `.ts`
  imports so Node runs it unbuilt, reaches the domain only through `src/domain`.
- `scripts/build-fixtures.mjs`: manual dev tool, never part of `npm run build`. Input: a raw
  transcript outside the repo, label, provenance, items JSON. Output: `src/fixtures/<name>.json`.
- Items come from the reference implementation: `scripts/autopsy-check.py --items-json`.
- Home paths redacted to `/home/dev/…`; session ids replaced by the fixture name.
- Expected values live in `src/domain/pending/*.expected.test.ts`, excluded from the default
  `vitest run`, executed by `npm run test:pending`, red until `analyze` exists.

## Acceptance criteria

- `src/fixtures/healthy-run2.json`, `constructed-ticket.json`, `constructed-file-edit.json`
  exist, validate against the contract types (a typecheck of `src/fixtures/index.ts`), and each
  carries exactly the four pre-labeled items with origins that point at real message uuids and
  lines in that fixture's `messages`.
- `fromSessions('fixtures', …)` lists three sessions; `pickDefault` returns `healthy-run2`.
- The three `Session.provenance` values are as in the storyboards; both constructed notes are
  present and shown by the UI later.
- `scripts/build-fixtures.mjs` regenerates `healthy-run2.json` byte-identical from the run 2
  transcript and the items JSON; the constructed fixtures are derived from it by a documented,
  re-runnable edit script (`scripts/construct-fixtures.mjs`), not by hand-editing JSON.
- `grep -rE '/Users/|charlesahn' src/fixtures` finds nothing.
- `src/domain/pending/` holds one expected test per fixture with every item's status, score,
  downstream result (and hit fields where matched), and restatement; `npm run test:pending`
  fails only because `analyze` does not exist; `npm run check` stays green.
- The adapter round-trips the run 2 transcript: `messages` count and `compactions[0].preTokens`
  equal the transcript's, and no excerpt exceeds 200 characters.
- A list of pushed-back type changes, each with the reason, is recorded in this file under
  "Type feedback" before close.

## Type feedback

1. **`Message.action` added (`ToolAction`).** Stage 4 matches on file paths, command text, added
   lines, and MCP input; a 200-character excerpt cannot carry an Edit's new lines or a comment
   body, so survival scoring would have run in the browser but downstream matching could not.
   Applied: `ToolAction { tool, toolUseId, filePath?, command?, addedText?, mcpInput? }` on
   tool_use messages, capped at 4000 characters per text, redacted like everything else.
2. **LOST versus non-anchor entities. Needs a ruling.** The don't-modify item has two entities,
   `scripts/rotate_keys.sh` and `rotate_keys.py`. In the file-edit fixture the summary drops
   every mention of the `.sh` file but keeps `rotate_keys.py` throughout, because building it
   was the work. Under the contract's DEGRADED clause ("any entity present anywhere in the
   summary") the item is DEGRADED, not LOST as the storyboard says. Two valid rules: keep the
   clause as written and change the storyboard to DEGRADED, or make the status rules use the
   item's anchor entities when it has anchors (the `.sh` path) and all entities otherwise. Not
   applied; the constructed fixture is built as storyboarded and the expected value follows the
   ruling.
